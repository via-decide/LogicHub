Tool purpose

Define the local-first service surface that lets hardware be operated, inspected, configured, updated, and diagnosed without depending on cloud infrastructure.

This tool is used when a device needs a trustworthy local service layer: a dashboard, USB/serial service shell, local HTTP API, MQTT bridge, ROS2 bridge, factory fixture endpoint, or offline maintenance panel.

Core rule: the API may request actions, but hardware safety and firmware interlocks own final authority. A browser button is never a substitute for a physical E-stop, fuse, relay interlock, thermal cutoff, or safe power path.

Implementation checklist

Pass / fail gates

  1. PASS-01 The device can be identified locally without cloud access.
  2. PASS-02 The operator can see health, state, fault, and version locally.
  3. PASS-03 Dangerous commands are impossible unless physical and software gates are satisfied.
  4. PASS-04 Every command returns a structured response with status, code, message, and timestamp.
  5. PASS-05 Power cycle does not erase fault history needed for diagnosis.
  6. PASS-06 A factory test receipt can be generated from a clean device using only local tools.
  7. PASS-07 Network loss does not leave motors/heaters/relays/charging in an unsafe state.
  8. PASS-08 A failed firmware/config update rolls back or enters a clearly visible recovery state.

Minimal local API pattern

Start read-only. Add configuration and actuation only after safety preconditions are validated.

MethodEndpointPurpose
GET/api/v1/identityRead product identity, serial, hardware revision, firmware revision, API version.
GET/api/v1/healthRead aggregate health state: ok/warn/fault/lockout.
GET/api/v1/stateRead current operating mode and state-machine node.
GET/api/v1/faultsRead active and historical fault codes.
GET/api/v1/logs?limit=100Read bounded local event log.
POST/api/v1/command/stopRequest software stop; not a substitute for hardware E-stop.
POST/api/v1/calibration/startStart a calibration routine when safety preconditions are true.
GET/api/v1/receipts/latestRead latest validation or command receipt.
POST/api/v1/configWrite configuration only after schema validation and compatibility check.
POST/api/v1/update/stageStage signed firmware/config update; do not activate until verified.

Example command gate pattern

// Local API command gate pattern: dangerous command routing
// Rule: network/UI command can request motion, but hardware safety owns final authority.

enum CommandClass { OBSERVE, CONFIGURE, CALIBRATE, ACTUATE, UPDATE, EMERGENCY };
enum SafetyState { SAFE_OK, SAFE_WARN, SAFE_FAULT, SAFE_LOCKOUT };

struct ApiCommand {
  const char* name;
  CommandClass klass;
  bool requires_physical_enable;
  bool requires_interlock_ok;
};

bool physical_enable_present();      // keyed switch, local button, service jumper, or safe fixture
SafetyState read_interlocks();       // E-stop, guard, battery, thermal, relay, sensor freshness
void emit_receipt(const char* command, const char* status, const char* code);

bool authorize(ApiCommand cmd) {
  if (cmd.klass == OBSERVE) return true;

  if (cmd.requires_physical_enable && !physical_enable_present()) {
    emit_receipt(cmd.name, "blocked", "NO_PHYSICAL_ENABLE");
    return false;
  }

  SafetyState s = read_interlocks();
  if (cmd.requires_interlock_ok && s != SAFE_OK) {
    emit_receipt(cmd.name, "blocked", "INTERLOCK_NOT_OK");
    return false;
  }

  return true;
}

// Example policy
ApiCommand motor_enable = {"motor_enable", ACTUATE, true, true};
ApiCommand read_health  = {"read_health",  OBSERVE, false, false};
