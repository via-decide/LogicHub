Universal Hardware Production Stack · T09

Actuator / Motor / Heater Safety Interlock

Use when a project can move, heat, switch mains, spin, charge, cut, crush, or energize something hazardous. The rule: software may request energy, but independent safety gates decide whether energy is allowed.

High-energy output boundary

Purpose

This tool converts actuator, motor, heater, relay, charger, blade, gantry, wheel, propeller, and hotend hazards into a repeatable production checklist. It forces each project to declare energy source, default-off behavior, physical stop path, firmware safe state, sensor-valid gates, commissioning receipts, and release blockers.

arm / disarm physical E-stop watchdog heater cutoff motor inhibit relay lockout test receipt
Safety boundary

This HTML is a planning and evidence tool. It is not a safety-rated controller, certified EVSE, certified machine guard, flight controller approval, industrial PLC design, or legal compliance certificate.

For real products, use qualified review, physical interlocks, fuses/breakers, isolation, wiring standards, certification where applicable, and local operating rules.

When to use this tool

Motion

Wheels, legs, gantries, belts, rotators, drones, toolheads, pumps, servos, steppers, BLDC motors.

Heat

Hotends, heated beds, barrels, injection heaters, sheetpress heaters, thermal chambers, soldering/curing rigs.

Power switching

Relays, SSRs, contactors, EVSE outputs, solenoids, VFDs, machine control boxes, battery outputs.

Pass / fail gates

GateRequired proofBlocked if missing
G0 — Hazard declaredHazard class, energy source, maximum current/temperature/force, and user exposure are documented.No hazardous output can be wired.
G1 — Default-off proofOn reset and firmware crash, actuator/heater/relay output is physically disabled.Board cannot enter powered test.
G2 — Physical stop proofE-stop/disconnect/fuse path is independent of software UI and network.No user-facing operation.

Example safety-chain pattern

Battery / mains→ Fuse / breaker→ Physical E-stop / disconnect→ Safety relay / enable→ Motor driver / heater SSR / contactor→ Actuator / load

Control path is separate: UI → MCU/Linux/ROS → command request → firmware gate → enable request. The physical safety chain must still be able to remove energy without trusting software.

// Firmware-side pattern: request energy only after physical and logical gates pass.
enum State { BOOT, DISARMED, SELFTEST, ARMED, ACTIVE, FAULT_LATCHED };

safe_output_off();

if (reset_or_boot) state = DISARMED;

while (true) {
  read_estop();
  read_sensors();
  read_command_heartbeat();

  if (estop_open || watchdog_expired || sensor_invalid || overcurrent || overtemp) {
    safe_output_off();
    latch_fault();
    state = FAULT_LATCHED;
  }

  switch (state) {
    case DISARMED:
      safe_output_off();
      if (operator_arm && physical_gate_ok && selftest_required) state = SELFTEST;
      break;

    case SELFTEST:
      if (selftest_pass && heartbeat_present) state = ARMED;
      else if (selftest_fail) state = FAULT_LATCHED;
      break;

    case ARMED:
      if (valid_motion_or_heat_command && limits_ok) state = ACTIVE;
      break;

    case ACTIVE:
      apply_limited_output();
      if (command_timeout) state = DISARMED;
      break;

    case FAULT_LATCHED:
      safe_output_off();
      if (fault_cleared_by_human && physical_gate_ok) state = DISARMED;
      break;
  }
}
