1. Tool purpose

Storage Integrity + Transactional Updates is the persistence discipline for universal hardware. It prevents a product from appearing usable while its memory, configuration, logs, firmware, calibration, or manifest has already become corrupt.

The tool defines how data is written, verified, committed, rolled back, backed up, and reported to the user. It applies to SPI NOR, SPI NAND, EEPROM, FRAM, SD cards, eMMC, USB mass storage, Linux filesystems, microcontroller flash, local databases, and validation receipts.

Prepare record→Write staging copy→Flush/sync→Read back→Verify CRC/SHA→Commit pointer→Keep rollback
Production rule: if a write cannot be interrupted safely, it is not a product feature yet. It is only a lab script.

4. Core transaction pattern

For most small hardware products, do not overwrite active state directly. Write a new candidate, verify it, then atomically move the active pointer.

ACTIVE_A: generation=41, valid=true, hash=...
ACTIVE_B: generation=42, valid=true, hash=...  ← boot chooses this
STAGING : generation=43, valid=false

update procedure:
1. write payload to STAGING
2. write metadata except valid flag
3. flush/sync storage
4. read payload back
5. verify CRC/SHA/schema/device compatibility
6. set valid flag / commit marker last
7. update active pointer or allow boot scanner to select highest valid generation
8. preserve older valid slot until new slot survives reboot test
Do not do this: open active config, erase it, write new content, then hope power stays alive. That creates silent bricking and unrecoverable state.

7. Clean checklist

  • Identify every write path before writing firmware or scripts.
  • Never overwrite the only valid copy of configuration, identity, or manifest.
  • Write payload first, commit marker last.
  • Read data back after write and verify checksum/hash before activation.
  • Use generation counters to choose newest valid data after reboot.
  • Bind calibration files to device serial, hardware revision, operator, date, and test fixture.
  • Separate caches from safety-critical state. A cache may be deleted; a manifest cannot.
  • For flash, record erase-block/sector geometry and write-size alignment.
  • For SD/eMMC/Linux, call sync/fsync for critical files and test real unplug behavior.
  • For firmware updates, keep known-good rollback until new image proves it can boot and serve health status.
  • For logs, make records append-only and tolerate corrupt tail truncation.
  • Display human-readable fault state when storage integrity fails.
  • Do not hide storage errors behind generic “failed” messages.

10. Example record layout

struct StorageRecordHeader {
  magic[4]        = "VDSR";        // record identity
  version         = 1;             // schema version
  object_type     = MANIFEST;      // manifest/config/log/calibration/firmware pointer
  generation      = 43;            // monotonic counter
  payload_length  = 4096;          // bytes after header
  payload_crc32   = 0x00000000;    // accidental corruption check
  payload_sha256  = "...";        // stronger identity / manifest link
  hardware_id     = "BOARD-REV-A"; // compatibility binding
  flags           = STAGING;       // STAGING until final commit
}

commit rule:
- write header with STAGING flag
- write payload
- flush/sync
- read back and verify CRC/SHA
- rewrite only final flag or pointer as VALID
- never mark VALID before verification

11. Example firmware logic pattern

result_t storage_commit(object_type, payload):
    old = scan_newest_valid(object_type)
    slot = choose_inactive_slot(object_type)

    erase(slot)
    write_header(slot, state="STAGING", generation=old.generation + 1)
    write_payload(slot, payload)
    flush_storage(slot)

    check = read_payload(slot)
    if crc32(check) != expected_crc or sha256(check) != expected_sha:
        mark_quarantined(slot, reason="VERIFY_FAILED")
        display_error("Storage verify failed; old state kept")
        return FAIL_OLD_STATE_ACTIVE

    write_commit_marker(slot, state="VALID")
    flush_storage(slot)

    boot_test_required = true
    return PASS_NEW_STATE_STAGED

boot_recover(object_type):
    candidates = scan_all_slots(object_type)
    valid = filter(validate_header_crc_sha_schema, candidates)
    if not valid:
        display_error("No valid storage record")
        enter_recovery_mode()
    else:
        activate(max_generation(valid))

15. Production rule

A hardware product is not trustworthy because it stores data. It is trustworthy only when it can prove which data is valid, which data is stale, which data is corrupt, what changed, what survived interruption, and what the user should do next.

Default decision: if the device cannot survive interrupted writes without silent corruption, block production and keep it in lab-only status.
