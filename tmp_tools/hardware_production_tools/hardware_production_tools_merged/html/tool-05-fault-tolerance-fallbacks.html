1. Tool purpose

Fault tolerance means the product expects failures and has deterministic fallback behavior. The user should see a clear state, the hardware should protect itself, and the system should preserve evidence.

Normal operation→ Fault detected→ Unsafe outputs disabled→ State shown locally→ Evidence logged→ Recovery or service gate

This tool is used whenever firmware, storage, sensors, bus communication, boot flow, motors, heaters, chargers, cameras, robots, or machines can fail in a way that affects usability or safety.

2. Core fault classes

Bus timeout

SPI/I2C/UART/CAN/USB device stops responding. Use timeout, retry budget, bus reset, and fault display.

Common

Storage corruption

Manifest, config, firmware, rootfs, calibration, or log becomes invalid. Use CRC/SHA, dual records, rollback.

Critical

Sensor invalid

IMU, LiDAR, camera, encoder, microscope, RF chain, or temperature sensor returns missing or impossible data.

Commissioning gate

Actuator stuck

Motor, relay, heater, valve, gantry, charger relay, or drone ESC remains active when it should stop.

Safety gate

Watchdog reset

Firmware or service hangs. Hardware/software watchdog resets into known safe boot mode.

Recoverable

Brownout / power sag

Supply droop causes MCU/SBC/storage failure. Detect, stop write, log reason, prevent partial update.

Corruption risk

5. Implementation checklist

Firmware rules

  • Every peripheral transaction has a timeout.
  • Every retry loop has a maximum retry count.
  • Every critical process feeds the watchdog only after passing health checks.
  • Every unsafe output has a single default-safe value.
  • Every recoverable fault has a clear error code and recovery path.
  • Every non-recoverable fault latches until user/service acknowledgement.

Hardware rules

  • Reset, boot, chip-select, enable, and hold pins have defined states.
  • Motor/heater/relay enables default to OFF during reset.
  • Brownout state cannot produce a half-write or half-energized output.
  • Test points exist for power rails, reset, bus lines, and fault inputs.
  • Physical E-stop exists wherever motion, heater, relay, blade, or charger risk exists.
  • Fault handling does not depend only on a browser or cloud UI.

8. Example wiring / logic pattern

Hardware pattern

MCU_RESET_N  ← supervisor / manual reset / watchdog reset
FAULT_LED    ← MCU GPIO, default OFF until firmware owns it
ACT_EN       ← MCU GPIO with pulldown, default DISABLED
SPI_CS_N     ← pullup, never float during reset
FLASH_WP_N   ← defined level, no accidental writes during boot
ESTOP_IN     ← normally-closed chain, independent of browser/cloud
FAULT_OUT    → optional latch / relay driver / motor inhibit

Firmware pattern

boot():
  set_all_outputs_safe()
  read_reset_reason()
  validate_config_crc()
  validate_required_peripherals()
  if fault:
    enter_latched_fault_mode(error_code)
  else:
    enable_runtime_watchdog()
    enter_idle_ready_state()

transaction_with_timeout(device, command):
  start_timer(TIMEOUT_MS)
  while not complete:
    if timer_expired:
      record_fault(device, TIMEOUT)
      set_all_outputs_safe()
      return ERROR_TIMEOUT
  return validate_response()
