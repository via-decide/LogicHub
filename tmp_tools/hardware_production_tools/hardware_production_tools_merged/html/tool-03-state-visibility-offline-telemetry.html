Use when

Use this tool whenever the device must show status, warnings, progress, readiness, or failure locally.

Rule: if the user has to ask “what is the hardware doing?”, the telemetry design is incomplete.
  • Air-gapped modules cannot rely on cloud dashboards.
  • Robots and machines must show safe/unsafe states before motion.
  • Chargers, heaters, and power systems must show fault states immediately.
  • Lab instruments must show calibration and measurement confidence.
  • Manufacturing fixtures must emit pass/fail evidence.

StateMeaningUser action
IDLEPowered, safe, waiting.Insert module / start task.
READYInputs valid, interlocks clear.Proceed.

Reference architecture

1. Event
Button, cartridge, sensor, bus, motor, API, or safety transition occurs.
2. State reducer
Firmware converts raw event into canonical device state.
3. Priority resolver
FAULT overrides BUSY; safety overrides user command.
4. Local output
OLED/TFT/LED/buzzer/log updates immediately.
5. Receipt
The state transition is recorded for QA or field service.
EVENT → STATE_REDUCER → PRIORITY_RESOLVER → LOCAL_OUTPUTS → RECEIPT

Fault priority:
ERROR / SAFETY_LOCKOUT
  > OVER_TEMP / OVER_CURRENT / LOW_BATTERY
  > BUSY / CALIBRATING / WRITING
  > READY
  > IDLE

Design checklist

  • Every state has a short name, human message, color/pattern, and recovery action.
  • FAULT states override all cosmetic animations and normal progress indicators.
  • Display works without internet, app login, or cloud dashboard.
  • LED pattern is readable even if OLED/TFT fails.
  • Critical errors persist long enough for the user to read them.
  • State transitions are logged with timestamp or monotonic counter.
  • Manufacturing fixture can read status via serial/USB/API.
  • Error messages never expose secrets, WiFi credentials, private images, or tokens.

Pass / fail gates

PASS: A first-time user can identify IDLE, READY, BUSY, WARN, and FAULT without a manual, internet, or serial console.
FAIL: Any safety-critical fault is visible only in logs, cloud UI, debug console, or hidden internal state.
GatePass conditionFail condition
Boot visibilityPower-on sequence shows power, MCU/app boot, and ready/fault.Blank or ambiguous startup.
Fault mappingEvery fault has unique code + plain message.Multiple faults show same generic error.
Offline operationState visible without cloud, phone, or network.User needs external dashboard for basic state.
Safety prioritySafety/fault overrides normal UI.Animation or progress hides fault.
Manufacturing QAFixture can force and verify each state.States cannot be tested deterministically.

Example state contract

enum DeviceState {
  STATE_IDLE,
  STATE_READY,
  STATE_BUSY,
  STATE_WARN,
  STATE_FAULT
};

typedef struct {
  DeviceState state;
  const char *code;       // e.g. E_SPI_TIMEOUT
  const char *message;    // e.g. "Cartridge read failed"
  const char *action;     // e.g. "Remove and reinsert cartridge"
  uint8_t rgb_r, rgb_g, rgb_b;
  uint16_t blink_ms;
  bool latch_until_ack;
} StatusFrame;

Example output policy

function publishStatus(frame):
  if frame.state == FAULT:
    stop_normal_animation()
    set_rgb(RED, fast_blink)
    oled_print(frame.code, frame.message, frame.action)
    log_event(frame)
    require_user_ack()
  else if frame.state == BUSY:
    set_rgb(BLUE, pulse)
    oled_progress(current_operation)
  else if frame.state == READY:
    set_rgb(GREEN, steady)
    oled_print("READY", "Safe to start")
