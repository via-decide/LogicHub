Tool 12 — Manufacturing QA Fixture + Test Receipts

Reusable production tool for turning prototypes, open-source hardware builds, and local-first devices into repeatable, evidence-backed manufacturing checks.

Tool ID: T12 Scope: QA fixtures Output: pass/fail receipts Applies to: 14 project bundles

1. Tool purpose

Manufacturing QA Fixture + Test Receipts makes hardware production repeatable. A prototype is not production-ready until another person can connect it to a fixture, run the same bounded test, capture the same evidence fields, and make a consistent release decision.

Input Unit under test, manifest, BOM, firmware, fixture script, operator, limits.
Process Inspect, power, probe, command bounded actions, inject faults, capture logs.
Output JSON receipt, CSV measurements, log hashes, PASS/FAIL/REWORK decision.
Production value Converts manual confidence into machine-readable evidence.

2. When to use this tool

  • Before sending a PCB, robot, printer, charger, camera node, microscope, or machine to a user.
  • When an open-source project is copied, localized, modified, or prepared for supplier review.
  • After any firmware, BOM, CAD, wiring, enclosure, or power-path change.
  • Before claiming a build is reproducible, safe to test, or ready for a pilot deployment.

5. Checklist

  1. Fixture definition: Identify what the fixture touches, powers, measures, and refuses to operate.
  2. Source version pinning: Record board revision, firmware commit, CAD revision, BOM version, operator, date, and fixture version.
  3. Pre-power inspection: Visual inspection, polarity, fuse, connector orientation, fastener state, wiring strain relief, and known safety blockers.
  4. Power rail test: Measure input, intermediate, and logic rails under no-load and controlled-load conditions.
  5. Continuity and isolation: Confirm expected nets are connected and forbidden shorts are absent before firmware interaction.
  6. Firmware identity: Read firmware version, bootloader/build ID, target profile, and configuration hash.
  7. Peripheral smoke test: Probe required buses and devices: SPI, I2C, UART, USB, CAN, camera, storage, sensor, motor driver, relay, or heater.
  8. Functional command test: Run bounded commands only: no-prop, wheels-on-blocks, heater-low-power, read-only API, or no-load motion first.
  9. Fault injection: Unplug sensor, corrupt config, timeout command, brownout simulation, emergency stop press, watchdog hold, or over-temperature flag.
  10. Evidence capture: Generate pass/fail JSON, CSV measurements, photos if needed, log hashes, and operator sign-off.
  11. Release decision: Mark unit PASS, FAIL, QUARANTINE, REWORK, or ENGINEERING-ONLY with explicit reason.

6. Pass/fail gates

GateRequirementFail condition
G01No unprotected live powerFAIL if high-current battery, mains, heater, motor, relay, or actuator path lacks fuse/disconnect/interlock for the project class.
G02Fixture cannot command unsafe motion by defaultFAIL if test software can arm motors, heaters, relays, or blades without explicit safety mode and operator confirmation.
G03All critical rails within toleranceFAIL if measured rails are outside limits, sag during command, overshoot on boot, or brown out during workload.
G04All required device IDs match manifestFAIL if flash chip, IMU, LiDAR, motor driver, camera, MCU, SBC, or controller identity does not match build manifest.
G05Faults enter safe stateFAIL if unplugged sensor, bus timeout, watchdog trigger, API loss, E-stop, or corrupt config does not land in a visible safe fault state.
G06Receipt is reproducibleFAIL if test cannot be repeated by another operator using the same fixture version and manifest.

7. Risk table

IDRiskCauseControl
QA-001False passA script marks pass even though fixture coverage is incomplete.Every pass condition must map to a measured evidence field.
QA-002Unsafe automated actuationFixture moves motors/heaters/relays/blades while operator is exposed.Default to no-load/read-only; require explicit armed test mode and physical E-stop.

QA-005Golden sample biasFixture only works on one hand-tuned prototype.Test at least three units or repeat cycles before accepting process.
QA-006Hidden environmental failureThermal, vibration, dust, RF, outdoor, or battery effects are ignored.Add project-specific environmental checks.

8. Example fixture logic pattern

This pattern is intentionally conservative: identify, measure, test bounded function, inject one safe fault, and only then decide.

START
  load build_manifest.json
  scan unit serial / revision / operator
  require current-limited supply or safe project-specific power source

PRE_POWER
  visual_check_required = true
  verify fuse / disconnect / E-stop / no exposed live hazard
  if blocker: decision = QUARANTINE

POWER_ON
  measure rails
  if rail outside limits: decision = FAIL, power_off

IDENTIFY
  read MCU / SBC / firmware / device IDs
  compare against manifest
  if mismatch: decision = REWORK

SMOKE_TEST
  run read-only probes first
  run bounded actuator/heater/motor command only if safe mode is enabled
  record all measurements

FAULT_TEST
  inject safe timeout/unplug/config fault
  require visible safe state and receipt entry

DECIDE
  PASS only if all required gates pass
  write receipt JSON + CSV + log hashes
END
