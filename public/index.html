Fair questions, straight answers.

The things hardware engineering leads ask before they hand LogicHub a repository. Something else? dharam@viadecide.com

How is this different from a hardware design review checklist?

A checklist is a document you tick manually. LogicHub is a deterministic execution that runs automatically on every engineering PR — it reads your physical telemetry and BOM graph, evaluates them against fixed gate rules, and blocks the release if anything fails. The verdict is cryptographically signed. A checklist can be skipped under schedule pressure. A gate cannot.

Does LogicHub replace our QA team?

No. LogicHub is the verification layer that makes every gate decision auditable and repeatable — it handles the deterministic part so your QA engineers spend time on the judgment calls a rule graph cannot make. Think of it as adding a gatekeeper that never forgets a check, so your team can focus on the things that actually require human expertise.

What physical instruments does it accept data from?

The telemetry intake accepts sealed inspection data from micrometer, thermal, weight, and voltage measurement fixtures. Data is ingested directly from the QA fixture output into the pull request stream. The gate evaluation engine validates the payload hash before any gate runs — tampered or unsigned telemetry is rejected before evaluation begins.

Can it run without internet access?

Yes. Gate evaluation runs inside the Zayvora local execution runtime with repository egress denied. The entire gate pipeline — BOM graph evaluation, physical tolerance checks, telemetry validation, SHA-256 integrity verification — runs locally. The only thing that requires outbound access is the optional verdict posting step, which you can disable and handle yourself.

Does it store our hardware schematics or BOM data?

No. LogicHub evaluates your design files inside a local execution boundary and returns a signed verdict. Your schematics, BOM files, CAD step files, and firmware binaries are never transmitted or stored externally. The evidence bundle contains hashes of those files — not the files themselves — so you can verify integrity without exposing the designs.

How long does a gate run take?

Evaluation time depends on the complexity of the BOM graph and the number of telemetry payloads, but most gate runs complete in under 60 seconds locally. The deterministic execution model means there is no network round-trip latency — the gate clock starts when telemetry is submitted and ends when the signed verdict is produced.

What happens when a gate fails — who gets notified?

A failed gate blocks the release action in the workspace. The signed verdict identifies exactly which gate failed, which physical condition triggered it, and what the observed value was against the expected bound. Notifications go to the engineer who submitted the PR. The release cannot proceed until the failing condition is resolved and the gate run is re-executed clean.

Do you train on our telemetry or design data?

No. Your hardware telemetry, BOM data, and design files never leave the local execution boundary, so there is nothing to train on. The Zayvora deterministic runtime that evaluates your gates is trained on synthetic and open engineering datasets — not on customer data. We do not use the output of your gate runs to improve the model.
